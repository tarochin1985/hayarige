# 運営メモ

note の「運営の裏側」を書くための材料。**サイトには出ません。**

gitの履歴を見れば「何を直したか」は分かりますが、**「なぜそうなっていたか」**は
残りません。そこがいちばん読み物になる部分なので、ここに1行ずつ足していきます。

書き方は1件1ブロック。日付・見出し・何が起きていたか・どう直したか・数字。
`scripts/monthly_notes.py` がその月のぶんを拾ってレポートに入れます。

## 2026-09-06 ツイート画像からサムネイルが消えた

画像を作るときに、文字の大きさを決める処理が**書体の読み込みを待たずに**動いていた。
その結果、本文が大きいまま枠に収まらず、下に置いた配信サムネイル3枚がはみ出して切れた。
決め打ちの待ち時間（1.8秒）で済ませていたのが原因。

待ち時間ではなく「収まりの計算が終わった」という合図を待つように変更。あわせて、
サムネイルの枠は縮まない設定にして、**そもそも切れようがない形**にした。

## 2026-09-21 SNSアカウントのアイコンを、目分量ではなく測って切り出した

XもBlueskyもアイコンは**丸く切り抜かれる**。ハヤリゲーのロゴは
左下のコントローラーから右上の矢印へ斜めに伸びた形なので、正方形の四隅
——つまり丸で切られると真っ先に消える場所——に絵の端が来ていた。

最初は「だいたいこのくらい」で縮めて置いたが、下に余白が偏って中心がずれた。
そこでロゴを大きく描画して画素を数え、**絵全体が入る最小の円**を求めた
（中心 255.26, 232.09／半径 232.14）。その円をアイコンの円の86%に合わせる、
という計算で置き直したら一発で収まった。

背景色は4つ作って48pxに縮めて見比べた。タイムラインで一番読めたのは
**ブランド色の地に白いロゴ**。白地だと線が細く、小さくすると沈む。

## 2026-09-23 「今朝」は、半分以上の配信について嘘だった

コラムに「今朝」と書いていたのを、たろちんさんに指摘された。
「昨夜の配信をリアタイした視聴者にとっては、今朝の出来事ではなく
昨夜の出来事だと思っているだろうから」。時間軸を書き手ではなく
**読む人が配信を見たとき**に合わせる、という話。

好みの問題かと思って数えてみたら、**事実として間違っていた。**
直近10日・23,972本の投稿時刻を調べると、朝の集計に入っている配信の
**58%は前の日までに投稿されたもの**だった。投稿が多い時間は
18時（10.0%）・23時（7.7%）・0時（7.9%）で、18〜23時が39%、0〜8時が30%。
**夜に立って、朝の集計に入る。** 「今朝」と書けば、半分以上について嘘になる。

書いてよい形を2つに決めた。裏の取れた具体的な日時（data/daily の published に
投稿時刻がUTCで入っている）か、時間帯を言い切らないぼかした言い方。
たろちんさんの言う「厳密にやりすぎると表現の幅が狭まる」もそのとおりで、
「ひと晩で」「この数日」「〜ばかりが並ぶ日」のほうが、幅があるぶん安全で、
しかも時計の針を書くより強い。

あわせて、X投稿文の見出しの頭に ★ を入れることになった。
**★は make_card.py が出力時に足す。コラムのJSONには書かない。**
見出しはサイト・画像・投稿文の3か所に出るので、JSONに★を書くと
3か所すべてに出てしまう。★が欲しいのは投稿文だけだった。

## 2026-09-24 404の原因を、実物を見ずに決めつけた

Search Consoleから「インデックスに登録されない要因」の通知。
サイト内のリンクを総当たりで調べ、**全ページが `unknown.json` という
存在しないファイルへのリンクを持っている**のを見つけて、これが原因だと報告した。

**外れていた。** たろちんさんにSearch Consoleの中身を貼ってもらったら、
404はたった1本だった。

    https://hayarige.com/matome/archive/

原因は別の行だった。ページの型紙に、こういう予備の値が書いてあった。

    const P = DATA.paths || {home: './', archive: './archive/'};

ふだんは `DATA.paths` が入るので使われない。しかし**JSの中の文字列も
クロールの対象になる。** `./archive/` は /matome/ のページでは

## 2026-09-25 ダークテーマでSteamのボタンが白くなっていた

利用者からの報告。原因は1行だった。

`--tipbg` は**ツールチップの背景色**。明るいテーマでは濃い色、暗いテーマでは

文字とのコントラストは 13.2:1 と 8.6:1。どちらも測って確かめた。

**変数の名前が用途を表していないと、こういう流用が起きる。**

## 2026-09-25 `</script>` でページが丸ごと壊れた

検索ページを足したら、そのページのJavaScriptが全部動かなくなった。
`DATA is not defined`。原因はこれ。

ページの中身（page_body）は `__PAGEBODY__` に差し込むと同時に、
**`const DATA = {...}` の中にも入っていた。** 検索ページの中身には
`<script>…</script>` が含まれる。JSONの文字列の中であっても、
HTMLを読む側は `</script>` を見た時点でスクリプトを閉じてしまう。
そこでDATAの定義が切れ、以降が全部おかしくなっていた。

直し方は2つ。
 ・DATAから page_body を外す（そもそもJS側で読んでいない。同じHTMLが2回入って重くもなる）
 ・JSONを埋め込むときに `</` を `<\/` にする（値は変わらない）

**2つ目は、検索ページと関係なく潜んでいた穴だった。** コラムの見出しや
配信タイトルに `</script>` が入っていたら、その日のページが丸ごと壊れていた。

あわせて、検索の正規表現で `/` をエスケープし忘れていて、文字クラスの途中で
正規表現が閉じていた。これも同じ日に直した。

## 2026-09-25 見落としを機械に見つけさせる仕組みを入れた

たろちんさんからの問い ──「ポゴは毎朝のアラートでも拾えていなかった？

### なぜアラートに出なかったのか（原因は2つ）

1. **「確認待ち」に入るのは、題名の先頭に `【】` があるものだけだった。**
   末尾の `【】` は配信者名・事務所名のことが多いので判定では見ない、という
   設計（`match.leading_bracket`）は正しい。だがそのせいで
   `…ついに壊れる【Pogostuck/標準】` も `ポゴ2で一発アウト` も、
   **どこにも記録されずに消えていた。**
2. **先頭に `【】` があった2本は拾われたが、片方は `Pogostuck`、片方は `ポゴ`。**

- **A案（候補あり）** カタログのゲーム名の頭と一致した語。正式名を提案できる
  ので1チャンネルでも出す。Pogostuck はこれで出る
- **B案（見落とし?）** カタログに無く、直近**7日**で3チャンネル以上が使った語。

## 2026-09-26 記録のページから「アツい！」が毎回消えていた

たろちんさんの指摘 ──「『今このゲームがアツい！』の部分だけ過去のアーカイブに

毎日のコラムと急上昇の観測なのだから」。

### 何が起きていたか

その日のページ（`/d/2026-09-20/` など）は、**その日のうちに作られるときは
急上昇入りで作られていた。** 問題はそのあと。

辞書を直すと、手元に残っている30日分のページが全部作り直される。
そのとき渡していたのが `"rising": []` と `"momentum": {"ready": False}` だった。
つまり**辞書を直すたびに、その日いちばん大事だった情報だけが毎回消えていた。**
代わりに出ていた「この日いちばん広がったゲーム」は配信者数の多い順で、
順位表の言い換えでしかない。**兆しの記録にならない。**

最近は毎日のように辞書を直しているので、全ページが消えた状態になっていた。

### 直し方

作り直すときも、今日のページと同じように倍率を出すことにした。
倍率は「その日の件数 ÷ 直前6日の平均」なので、手元に日別データが残っていれば
後から同じ数字が出せる。前の日の集計は使い回す（`cal_hist` で覚えておく）。

- `pick_rising()` を切り出して、今日のページと記録のページで同じ基準を使う
- 記録のページの見出しは「この日アツかったゲーム」にした（過去の話なので）
- JavaScriptが動く前も正しい見出しが出るよう、型紙を `__HOTTITLE__` にした

手元の31日分を作り直して確認。全部に急上昇6件が入った。
7日の推移グラフも、ついでに記録のページで出るようになった（同じ計算で出る）。

### この先、二度と消えない理由

- その日のページは、**その日のうちに本物の急上昇入りで作られる**
- 作り直されるときも、同じ計算で入れ直される
- 30日を過ぎて配信タイトルを外すとき（`purge_old`）は、
  **`streams` だけを外して倍率・件数・ゲーム名は残す。** 規約にも合っている

`matcher_fingerprint()`（作り直すかどうかを決める印）に、
**`build_site.py` 自身も入れた。** 今回は型紙も一緒に直したから作り直されたが、
**組み立て方だけを変えた日は、直したのにページが古いままになる。**
作り直しは2〜3分かかるが、直したのに直らないほうが悪い。

## 2026-09-26 クォータ（続き）── 取り直さずに作り直せるようにした

たろちんさん ──「今日みたいにサイトの仕様を変える日は毎日の更新を複数回
回す必要があるし、現状だとまだまだそういう日は多い。気を付けていても足りなく

もっともな話だが、その前に気づいたことがある。

### 作りを変えた日に、配信を取り直す必要はない

「3. 毎日の更新」は**収集とサイト作りをまとめてやっている。**
だがコードや見た目を直した日にやりたいのは**サイトを作り直すこと**だけで、
配信を取り直す必要はない。同じ日にもう一度取っても中身はほとんど変わらない。

なのに1回回すたびに約2,500ポイント使っていた。**9月26日に使った
7,200ポイントのうち、5,000は要らなかった。**

そこで `.github/workflows/3-daily.yml` の手動実行に選択肢を足した。

```
配信を取り直す（サイトの作りを変えただけなら no でよい）  yes / no
```

**no なら1ポイントも使わない。** 定期実行のときは inputs が空になるので、
これまでどおり必ず取りに行く。

これで、作りを変えた日の消費は定期の2回ぶん（約5,000）だけになる。
何回作り直しても増えない。**申請しなくても足りる計算になった。**

### 申請そのものについて、気になることが出てきた

使用量の引き上げは「YouTube API Services - Audit and Quota Extension Form」
から申し込む。**申し込むと監査（compliance audit）が入る。**

その下調べで、開発者ポリシーの **III.E.2 Data Aggregation** を読んだ。

> Do not aggregate API Data except that you may only aggregate API Data
> relating to YouTube channels that are under the same content owner as
> recognized by YouTube pursuant to content licensing agreement(s) between
> YouTube and such content owner. Such aggregated API Data must only be
> viewable by that content owner.

素直に読むと「**別々の持ち主のチャンネルをまたいで集計して、それを公開しては
いけない**」と書いてある。当サイトがやっていることそのものである。

`.hot .g`（急上昇のゲーム名）に `white-space:nowrap` と

理由は、グリッドや横並びの升目が**既定で「中身の最小幅より狭くならない」**から。

## 2026-09-30 fix102 ── Blueskyへの自動投稿

Xは手で投稿するまま。Blueskyだけ「3. 毎日の更新」のついでに自動で出す。
**文も画像も、Xに貼っているものと同じ**（site/tweet.txt と site/card.png）。
別々に書き分けると、片方だけ直したときに食い違う。

### 鍵の置き場所

GitHubの Secrets に **`BLUESKY_APP_PASSWORD` の1つだけ**。
ハンドルは site_config.json の `bluesky_handle`（= hayarige.com）から読む。
**本体のパスワードではなく、Blueskyの「アプリパスワード」を使う。**
もれたらそこだけ取り消せる。

`post_bluesky.py` は環境変数からしか読まない。ファイルにも記録にも書かない。
Blueskyがエラーを返したときも、返ってきた説明文だけを出す。

### 二重投稿をどう防いだか

「3. 毎日の更新」は1日2回動く。素朴に書くと同じ話を2回投稿する。

**鍵にしたのは「コラムの日付」（data.json の column.date）で、「今日の日付」ではない。**
今日のコラムがまだ無い日、サイトは前の日のコラムを出し続ける。今日の日付で数えると
**同じコラムを日付だけ変えて何度も投稿してしまう。**
実際、9月30日の site/data.json の column.date は 9月29日だった。

投稿済みの日付は `data/bluesky_posted.json` に残す。ワークフローが git に積むので
次の回でも残っている。だから投稿のステップは「保存して公開」より前に置く。

### つまずきやすいところ ── 印（facets）はバイトで数える

**Blueskyは本文を見て勝手にリンクにしてくれない。**「何バイト目から何バイト目までが
URLか」をこちらが数えて渡す。ここで**文字数**を渡すと、日本語の投稿がまるごとずれる
（UTF-8ではひらがな1文字が3バイト）。必ずUTF-8にしてから数える。

タグの切れ目も要注意で、`#ハヤリゲー（9/30）🎮` を素朴に切ると
**全角の括弧から先までタグに入れてしまう。** 全角括弧・かぎかっこ・句読点で切る。

URLのほうは逆の失敗をした。最初「空白以外」で拾ったら
`https://hayarige.com。つづき` の句点から先まで飲み込んだ。
**URLに使える文字はASCIIだけ**なので、そこで切る。

確かめ方は、出した範囲でUTF-8を切り出して元の文字列に戻ること。
実際の投稿文＋8通りの変わった書き方で確認した。

### そのほか決めたこと

- 画像には**説明（alt）を必ず付ける。** 目の見えない人にも中身が伝わるように、
  注目ゲーム・見出し・上位3ゲーム・いちばん伸びたゲームを文にして入れる
- 画像の上限は1,000,000バイト。今の card.png は401,038バイトで収まっている。
  超えた日は**文だけ投稿する**（止めない）
- `langs: ["ja"]` を付ける。付けないと翻訳の案内が変なふうに出る
- 鍵が無い・コラムが無い・本文が300字超え … どれも**何もせず正常終了**する。
  ワークフローは continue-on-error なので、失敗してもサイトの更新は止まらない

### 直したいときの逃げ道

投稿を消したうえで `data/bluesky_posted.json` からその日付の行を消せば、
次の更新でもう一度投稿される。ファイルごと消してもよい（また作られる）。

## 2026-10-01 fix105 ── RSS（site/feed.xml）

X・Blueskyは「流れていく」場所で、その時間に見ていない人には届かない。
RSSは**読み手の側が取りに来る**ので、一度登録されればずっと届く。
ニュースをまとめて配る側（個人のまとめ、自動投稿のbot）にとっても、
RSSがあるかどうかで扱いやすさがまったく違う。

作るのは一度きりで、あとは毎日の更新に乗る。**運用の手間はゼロ。**

### 中身は「読みもの」だけにした

毎日のコラム（見どころ付き）と、週・月のまとめ。新しい順に最大40件。

**ランキングは入れていない。** 1日2回変わるので、入れると購読者の画面が
そればかりになる。RSSは「流れ」ではなく「読むもの」を配る場所。

**配信タイトル・チャンネル名の一覧も入れていない。** あれはYouTubeから
借りた文字で30日で消すものなので、配って歩く形にはしない。
コラム本文の中の引用は、こちらが書いた記事の一部なのでそのまま。

### つまずきそうなところ

**日付の書き方（RFC 822）は英語の曜日・月名で書く決まり。**
`strftime` の `%a` / `%b` は動かす場所の言語設定で変わるので、
日本語環境で作ると `木, 01 10月 2026` のような、購読アプリが読めない
日付になる。**曜日と月の名前は、自分で表を持って書いている。**

### 置き場所と見つけ方

  https://hayarige.com/feed.xml

型紙の `<head>` に宣言（`<link rel="alternate" type="application/rss+xml">`）を
入れたので、購読アプリはサイトのURLを入れるだけで見つけられる。
フッターにも「RSS」のリンクを置いた。

### 確かめたこと

- XMLとして正しく読めること（32件）
- 日付が `Thu, 01 Oct 2026 07:00:00 +0900` の形になっていること
- 週まとめも混ざって、新しい順に並んでいること
- トップ（`./feed.xml`）でも記録ページ（`../../feed.xml`）でもリンクが合うこと

## 2026-10-01 fix106 ── まとめのタイトルに固有名詞を入れる／月まとめもカードを出す

たろちんさんから。

> 記事のタイトルには「トルネコの大冒険」とゲーム名をはっきり書いたほうがいい。
> 「『トルネコの大冒険』新作が下がっていく月に、33年前のダンジョンだけ上がった」と
> 冒頭にゲーム名を足すだけでも何の話か明確に伝わる。

### なぜ毎日のコラムと決まりが逆になるのか

**毎日のコラムの見出しには、ゲーム名を入れない。**
サイトでもXの画像でも、見出しのすぐ上にゲーム名が大きく出ているので、
入れると同じ名前が2回並ぶ。

**週・月のまとめのタイトルには、冒頭にゲーム名を入れる。**
あちらは一覧でもカードでもXでも、**タイトルだけが単体で出る。**
固有名詞が無いと、読む人には何の記事か分からない。

**出る場所が違うから、決まりが逆になる。** これを書いておかないと、
あとで片方に合わせて「直して」しまう。EDITORIAL.md と README_まとめ.txt の
両方に、互いを指す形で書いた。

長いゲーム名はフルで入れずに縮めてよい（『トルネコの大冒険 ちょっとステキな
リマスター』→『トルネコの大冒険』）。全体で35字くらいまで。

### 月まとめもカードを出せるようにした

`make_week_card.py` が**週と月の両方**を受けるようにした。ファイル名で見分ける
（`2026-09-14` なら週、`2026-09` なら月）。札の文字が「月まとめ」になり、
見出しの右上が `2026.09` になり、投稿文の書き出しが「9月の #ハヤリゲー まとめ🎮」に変わる。

**名前は make_week_card.py のまま。** 月用に別のプログラムを作ると、
片方だけ直したときに見た目がすぐ食い違う。1本にしてある。

### タイトルを長くすると、投稿文がはみ出す

実際に試したら、38字のタイトルで **293文字ぶん**（上限280）になった。
**ゲーム名を入れるぶん、「こんなこともありました」は短くする必要がある。**

そこで警告を具体的にした。「超えています」だけだと何字詰めればいいか
分からず、何度も作り直すことになる。

    ⚠️ Xの上限を 13 文字ぶん超えています（約7字）。
       見出しを短くするか、「こんなこともありました」の2行を詰めてください。
       見出しにゲーム名を入れると長くなります。そのぶん
       『こんなこともありました』は1行30字くらいに抑えると収まります。

日本語は1字で2文字ぶん数えるので、超過の半分が削る字数の目安。

### 日本語のURLについて（聞かれたので調べた）

`https://hayarige.com/g/妹に運転を教える/` のようなURLは、**リンクとしては
機能する**（ブラウザが変換する。Xは全部 t.co に包むので飛び先も壊れない）。
ただし**見た目が保証されない。** 環境によっては
`%E5%A6%B9%E3%81%AB...` という記号の羅列で表示される。

**投稿に貼るURLには使わない。** 英語名のゲーム（`/g/apex-legends/`）か、
一覧の `/g/` を使う。サイト内のリンクとしては問題ない。

2026-10-01 月まとめのカードを「今月のハヤリゲー ベスト3」にした
------------------------------------------------------------
たろちんさんから:

> 月まとめのツイート用カードは週まとめと少し作り方を変えて
> 「今月のハヤリゲーベスト3」とかにしたらどうだろう。1位は大きめに表示、

月まとめは「今月伸びたゲーム3本」が記事の骨で、見出しも要約もその1位の話に

あちらは「出来事」を書くもので順位が無いので、形を変える理由が無い。

    1位 … ゲーム名を大きく ＋ コラムの見出し ＋ 要約（card.sub）
    2位 3位 … 「こんなこともありました」があった場所へ、横並びで

名前は `card.best` に書く。省いても `sections` の小見出し（「1位 ◯◯」）から
拾うので落ちない。`best` を書くのは**通称に縮めたいとき**と、2位・3位に
ひとことを足したいときだけ。

### 見出しの頭のゲーム名は、カードの中だけ落とす

まとめのタイトルは冒頭にゲーム名を入れる決まりにした（9/30）。ところが
ベスト3の札では、その名前を1位としてすぐ上に**大きく出す。** そのままだと
同じ名前が2行続く。

    1位 トルネコの大冒険
    ★ 『トルネコの大冒険』新作が下がっていく月に、33年前の…   ← 2回出る

なので札の中だけ頭の『…』を外す。外すのは、かぎかっこの中身が1位の名前と
重なるときだけ（別のゲームの名前かもしれないので）。毎日のカードで見出しに
ゲーム名を入れないのと、理由はまったく同じ。**出る場所で決まる。**

### 長い名前は、はみ出す前に小さくしておく

『エースコンバット8 ウイングス・オブ・シーヴ』で2行目に「ーヴ」だけ
こぼれた。描いてから縮める仕掛け（FIT）は「画像からはみ出したら」しか
効かないので、2行で収まってしまう名前には働かない。**1行に入る大きさを
先に当てる**ようにした（字数ではなく幅で測る。欧文は字数ほど幅を食わない）。
